Snowflake Clustering Depth

Performance Optimization Guide

What is Clustering Depth?

Clustering Depth is a performance metric in Snowflake that measures how well-organized your data is within micro-partitions. It quantifies the overlapping of data ranges across partitions for a specific set of columns (clustering keys).

The Metric

A value that represents the average number of overlapping micro-partitions for any given point in the data range.

The Goal

The lower the depth, the better. A depth of 1.0 means perfect alignment with no overlaps, enabling maximum partition pruning.

The Impact

Higher depth forces Snowflake to scan more micro-partitions for the same query, increasing time and credit consumption.

Before vs. After Optimization

HIGH DEPTH (POOR)

Micro-Partitions Sorted

Real-World Use Cases

Massive Fact Tables

Tables with TBs of data where natural ingestion order isn't sufficient for common filters.

Range-Based Queries

Optimization for queries using `BETWEEN` or comparison operators on dates/IDs.

Point Lookups

When queries look for specific records (e.g., CustomerID) in high-churn tables.

The Lifecycle of Data Clustering

1

Data Ingestion

New rows arrive in random or chronological order, creating micro-partitions.

2

Overlap Analysis

Snowflake tracks the Min/Max values of clustering keys for every partition.

3

Auto-Clustering

If depth is high, background service re-writes data to group similar values.

4

Pruning

Future queries "prune" (skip) irrelevant partitions, scanning only required data.

Understanding "Overlaps"

Imagine two folders: Folder A (Files with ID 1-50) and Folder B (Files with ID 40-90). They overlap on IDs 40-50. If a query asks for ID 45, Snowflake must open both folders. This is depth > 1.

Technical Implementation

1. Define Clustering Key

-- Create table with a key
CREATE TABLE sales_data (
  id INT,
  sale_date DATE,
  region STRING
) CLUSTER BY (sale_date);

-- Or add to existing table
ALTER TABLE sales_data
CLUSTER BY (sale_date, region);

2. Check Current Depth

SELECT SYSTEM$CLUSTERING_DEPTH(
  'sales_data',
  '(sale_date)'
);

Scenario Walkthrough

Initial State: You load 1 billion rows of web logs. Since data comes in real-time, it's roughly sorted by timestamp. Depth is ~10.

The Problem: Monthly reporting queries take 15 minutes because they have to scan almost the whole table.

The Fix: You enable Clustering on `(EVENT_DATE)`. Snowflake starts re-writing micro-partitions in the background.

Result: After 2 hours, Clustering Depth drops to 1.5. The same reporting query now completes in 2 minutes because Snowflake skips 80% of the partitions.

Pro Tip

Don't rush to cluster every table! Snowflake's Natural Ingestion Ordering (inserting data by time) is often "good enough." Only apply clustering keys to tables larger than multiple Terabytes where queries are consistently slow despite right-sized warehouses.
