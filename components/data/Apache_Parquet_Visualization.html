Big Data Architecture Columnar Storage

The Gold Standard of Columnar Storage

Apache Parquet is an open-source, column-oriented data file format designed for efficient data storage and retrieval. It provides high-performance compression and encoding schemes to handle complex data in bulk, making it the backbone of modern data lakes.

Columnar Format

Stores data by column rather than row. Perfect for analytical queries (OLAP) where you only need a subset of columns.

High Compression

Uses advanced encoding (Run Length, Dictionary, Delta) to reduce storage footprint by up to 90% vs CSV.

Nested Structures

Support for complex nested data types (JSON-like) while maintaining columnar efficiency using the Dremel algorithm.

The "Analytic Shift"

Before: Row-Based (CSV/JSON)

Reading 1 column requires scanning the entire file. High I/O overhead. Large uncompressed size.

After: Column-Based (Parquet)

"Projection Pushdown" allows reading only specific columns. Skip irrelevant data using metadata. Tiny storage footprint.

Real-World Applications

  • Data Lakes (AWS S3 / Azure Blob)

    Standard format for storing PBs of data efficiently for long-term retention.

  • Interactive Querying (Athena / Presto)

    Massive speed gains and cost reduction since AWS Athena bills by data scanned.

  • Machine Learning Pipelines

    Feeding feature sets into Spark or Python (Pandas/Polars) at high throughput.

Anatomy of a Parquet File

Row Group

Horizontal slice of rows (e.g., 128MB chunks)

Column Chunk

Data for a specific column within that row group

Page

The unit of compression and encoding (e.g., 1MB)

Footer (Metadata)

Schema, min/max values, and file offsets

The "Magic" of the Footer

Parquet stores the metadata at the end of the file. This includes min/max statistics for every column in every row group. Query engines read the footer first, identify which row groups contain the data needed, and "jump" straight to those locations, skipping millions of rows entirely.

Scenario: E-commerce Logs

We have 10 Billion rows of transaction logs. We only want to calculate the Sum of Revenue for Year 2023.

CSV: Scans 20 columns + 10B rows (1.2 TB)
Parquet: Scans 1 column + filtered row groups (45 GB)
pyspark_processing.py 
# Read Parquet from Data Lake
df = spark.read.parquet("s3://my-lake/transactions/")

# PySpark optimizes this automatically!
# It will only load 'revenue' and 'year' columns
result = df.select("revenue") \
           .filter(df.year == 2023) \
           .agg({"revenue": "sum"})

# Save back as partitioned parquet
result.write.partitionBy("year").parquet("output_path")

Avro is row-based. Best for write-heavy operations (streaming) where you need to access all fields of a record (OLTP).

Parquet is column-based. Best for read-heavy analytics (OLAP) where you only need a subset of columns. It offers much better compression for similar data types.

It's an optimization where the filtering logic is "pushed" to the storage layer. Instead of reading the whole file and filtering in memory, the engine uses Parquet metadata (min/max/null counts) to determine if a Row Group can be skipped entirely before reading it.
To maintain high compression ratios and complex columnar structure, files cannot be "updated" in place. To change a row, you must rewrite the whole file (or use frameworks like Delta Lake/Iceberg that manage "deltas" on top of Parquet).

Interview Pro Tip

If asked about "Schema Evolution," mention that Parquet supports adding columns to the end of a schema, but removing or changing types requires careful coordination or tools like the Glue Data Catalog. This shows you understand the practical governance of file formats.
